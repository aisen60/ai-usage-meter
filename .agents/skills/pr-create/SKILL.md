# PR Create

为当前分支创建 GitHub Pull Request。以执行时的 Git、GitHub CLI 和开发者确认作为唯一事实来源；不要凭对话概述猜测变更、版本或提交范围。

## 交互顺序

遵循以下顺序。每次仅提出一个尚未解决的关键问题。

1. 首次面向开发者的提问必须是：`PR 标题和摘要要使用什么语言？`
2. 然后询问：`这次 PR 要创建为可合并的 open，还是草稿 draft？`
3. 然后询问是否要在 `CHANGELOG.md` 记录本次版本的修改内容。
4. 完成只读预检和差异分析，生成 PR 标题、摘要和可选的 Changelog 草案。
5. 将完整 PR 摘要发给开发者审核。开发者要求修改时持续修订并再次审核。
6. 只有开发者明确批准标题和摘要后，才执行 Changelog 写入、Git 提交、推送和 PR 创建。

PR 标题和摘要使用开发者在第 1 步选择的语言。`CHANGELOG.md` 新增内容始终使用中文。Git commit 的人类可读信息默认使用中文，遵循 `$git-commit` skill。

## GitHub 网络与沙箱

GitHub CLI 和 Git 远端操作需要网络；沙箱可能无法访问 GitHub 的 DNS 或 HTTPS 服务。因此，沙箱内的 `gh auth status`、`gh repo view`、`gh pr ...`、`gh api` 或 `git push` 失败时，不得直接判断为未认证、远端错误或权限不足。

- Agent 可以按平台权限机制请求在沙箱外、具备网络的环境中执行 GitHub 相关命令。范围包括 `gh auth status`、仓库/PR 查询、GitHub API、推送和创建 PR；应保持命令和目标仓库范围最小。
- 如果沙箱内错误属于 DNS、网络连接、TLS、代理或无法访问 GitHub，先在沙箱外重试同一个只读命令，再判断认证或远端状态。
- 需要写入 GitHub 的命令仍必须遵守本 skill 的审核与批准门禁；沙箱外执行只解决网络环境，不会绕过标题/摘要批准、提交范围确认或推送规则。
- 沙箱外重试仍明确报告未认证或无权限时才停止并报告；不得读取、导出、记录或要求开发者暴露 token、cookie 或认证载荷。

## 只读预检

在生成草案前，检查以下状态：

- `gh` 已安装且 `gh auth status` 成功；远端对应 GitHub 仓库。若沙箱内因网络失败，按“GitHub 网络与沙箱”规则在沙箱外复核。
- 当前 HEAD 不游离，且当前分支不是 GitHub 仓库默认分支。
- 通过 `gh repo view --json defaultBranchRef` 读取仓库默认分支；PR 的 base 必须使用该分支，不能使用当前分支的上游分支推断替代。
- 工作区、暂存区、当前分支相对默认分支的完整差异，以及受影响文件。
- 当前 head 分支是否已有 GitHub PR。

若在沙箱外复核后 `gh` 仍不可用或未认证、远端不是 GitHub、默认分支无法读取、当前分支游离/即默认分支、没有可提交的目标变更，停止并报告原因。不要写入文件、提交、推送或创建 PR。

若当前分支已有 PR，报告 URL 和状态，不要创建重复 PR；更新既有 PR 应使用未来的 `pr-update` workflow。

若发现无法安全归属到本次 PR 的未提交改动，列出文件并要求开发者确认提交范围；不要自动把它们纳入提交。

## Changelog 与摘要

基于真实 diff 生成：

- 一个符合开发者所选语言的 PR 标题；
- 结构化 PR 摘要，至少包含变更内容、影响范围、验证情况和风险/未验证项；
- 如果开发者选择更新 Changelog，则生成对应的中文 Changelog 条目草案。

Changelog 草案必须延续现有 `CHANGELOG.md` 的版本标题和分类小节格式。可从受影响工程设置、版本文件和当前分支变更一致确定版本号时才使用它；否则询问开发者版本号，不能猜测或创建不确定的版本标题。

在聊天中完整展示标题、摘要和可选 Changelog 草案，明确请求审核。开发者不满意时只修改草案并继续审核；在得到明确批准前，保持只读，不修改 `CHANGELOG.md`。

## 批准后的操作

开发者明确批准后，按以下顺序操作：

1. 如已批准更新 Changelog，将已审核的中文条目写入 `CHANGELOG.md`。
2. 使用 `$git-commit` skill 检查完整差异、仅显式暂存开发者确认的文件、排除无关改动与敏感信息，并创建适当的中文 Conventional Commit。
3. 验证提交结果后，推送当前分支；不强推。
4. 以当前分支作为 head、GitHub 仓库默认分支作为 base，使用已批准的标题和摘要执行 `gh pr create`。选择 `draft` 时添加 `--draft`，选择 `open` 时不添加该参数。
5. 返回创建成功的 PR URL、分支和提交信息。

不得在批准前写入 Changelog、提交、推送或创建 PR。不得自动拉取、合并、变基、解决冲突、修改已有 PR、强推或回滚已经完成的 Git 操作。

## 失败边界

- Changelog 写入或 Git 提交失败：停止；不要推送或创建 PR。
- 推送失败：停止；不要创建 PR。报告已创建的本地提交和推送错误。
- PR 创建失败：保留已经完成的提交和推送，重新检查当前 head 是否已有 PR，报告结果与 GitHub 错误；不要重复创建。
- 任何需要开发者决策的歧义（提交范围、版本号、认证/权限修复）都应停止并询问，不自行扩大操作范围。

不要记录、持久化或在回复中暴露 token、cookie、账号标识、认证载荷或完整私有响应。
